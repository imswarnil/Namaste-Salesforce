Objects, fields and records

Article 18 min Beginner

Every Salesforce feature you will ever touch — reports, Flows, Apex, Agentforce — is built on three words: objects, fields and records. Get these three right and the rest of the platform reads like a well-labelled map. Get them wrong and every later decision costs twice.

What an object really is

An object is a table with opinions. It has columns (fields), rows (records), and a set of rules the platform attaches for free: a page layout, a tab, list views, sharing, history tracking, an API name. When you create Invoice__c you are not just adding a table — you are adding a noun to the language your org speaks.

Note

The API name is forever. You can rename the label from "Invoice" to "Bill" tomorrow; Invoice__c stays in every Flow, report and line of Apex that ever referenced it.

Standard vs custom

Standard objects arrive with the licence and carry years of platform behaviour: Opportunity knows about stages and forecasts, Case knows about queues and entitlements. Custom objects are a blank noun. The rule of thumb is simple — if a standard object already means what you mean, use it.

QuestionStandard objectCustom object
Built-in behaviour stages, forecasts, entitlementsnone — you build it
API namefixed, e.g. Opportunityyours, always ends in __c
Reportingreport types ship readycreate a custom report type
When to choosethe noun already existsthe business has a noun the platform lacks

Naming that survives

Name objects as singular nouns a new hire would say out loud: Invoice, not InvoiceData. Name fields for what they hold, not where they came from: Due Date, not SAP_DueDate.

Tip

Write the field's description and help text at creation time. Six months later they are the only documentation that exists.

Fields are promises

A field's type is a promise about the data inside it. A Date field promises a real date; a Picklist promises one of a known set; a Lookup promises a record on another object. Code and automation trust those promises — which is exactly why a free-text field holding "TBD" breaks a Flow at 2 a.m.

AccountService.cls
// The field type is the contract. Apex trusts it.
public with sharing class AccountService {
    public static Date nextRenewal(Account acct) {
        if (acct.Renewal_Date__c == null) {
            return Date.today().addMonths(12);
        }
        return acct.Renewal_Date__c.addYears(1);
    }
}
Watch out

Changing a field's type after data exists can silently truncate or null values. Treat a type change as a migration, not an edit.

Records and relationships

A record is one row. Relationships are fields that point at other rows, and the platform gives you three kinds — lookup, master-detail and the junction pattern built from two master-details.

Choosing a relationship

  1. Can the child exist without the parent?

    If no — an invoice line without an invoice is meaningless — use master-detail and inherit sharing.

  2. Do you need roll-up summaries?

    Native roll-ups only work over master-detail. Lookups need a Flow or DLRS.

  3. Will the parent ever change?

    Master-detail can be re-parented only if you tick the box at creation. Decide now.

Try it yourself

In a Developer Edition org, create a custom object called Invoice with a master-detail to Account and a roll-up summary on Account that sums Amount. Then create one Invoice and watch the Account update without a line of code.

Key idea

The data model is the one part of an org that every other part depends on. Spend the extra hour here; it repays itself in every Flow, report and class you write afterwards.

Key takeaways

  • An object is a table with platform behaviour attached; its API name never changes.
  • Use the standard object whenever it already means what you mean.
  • A field's type is a promise; automation and code trust it.
  • Master-detail when the child cannot exist alone or you need roll-ups; lookup otherwise.

Check your understanding

1. Which object should hold a customer's open deal?

Opportunity is the standard object for a deal in progress — stages, forecasting and products come with it. A custom object would rebuild all of that by hand.

2. You need the Account to show the total of all its invoices without code. Which relationship?

Roll-up summary fields work only across a master-detail relationship. A lookup needs a Flow or a package to sum the children.

3. After renaming the label "Invoice" to "Bill", what happens to Invoice__c in your Flows?

Labels are for humans; API names are for everything else. Renaming a label touches nothing that runs.
